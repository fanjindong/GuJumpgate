# 侧边栏页面步骤与手动恢复设计

## 背景

当前 GuJumpgate 侧边栏直接展示 workflow 节点，例如 `existing-account-login`、`hosted-checkout-submit`、`hosted-paypal-payment`。这种展示方式对开发者清楚，但用户遇到异常恢复时会难以判断应该继续哪个节点。

本次设计解决两个明确问题：

1. 侧边栏主步骤应按真实浏览器页面划分，而不是按底层节点平铺。
2. 流程中断后需要有手动恢复入口，尤其是已有账户已登录、Hosted Checkout 填写失败或用户刷新页面后继续填写。

## 已确认决策

- 主步骤采用“按浏览器页面划分”的方案。
- 恢复入口采用“页面级恢复 + 自动检测建议”的方案。
- 不把 workflow 根执行模型改成页面节点，避免扩大自动运行、日志、测试和节点执行器的改动面。
- 侧边栏不直接修改节点状态，所有恢复判断和状态修正都由后台统一处理。

## 目标

- 用户能按页面理解流程进度：ChatGPT 页面、认证页、Checkout 页面、PayPal 页面、开通结果。
- 用户遇到已有登录态时，可以确认跳过认证相关步骤并继续后续流程。
- 用户在 Hosted Checkout 填写失败或刷新页面后，可以接管当前页面继续填写，不必重新创建 Checkout。
- 用户已经跳到 PayPal Hosted 页面时，可以接管当前 PayPal 页面继续支付。
- 自动运行默认行为保持不变：点击“自动”仍从首节点重新开始；只有用户确认恢复时才从当前进度继续。

## 非目标

- 不重写 `workflow-engine` 的节点模型。
- 不把所有节点执行器合并成页面执行器。
- 不增加复杂的人工编辑节点状态功能。
- 不恢复旧注册、旧邮箱池或已删除的历史入口。

## 页面模型

在 `data/step-definitions.js` 的节点元数据中补充页面分组信息。PayPal Hosted 默认流程映射如下：

| 页面 ID | 页面标题 | 包含节点 | 说明 |
| --- | --- | --- | --- |
| `chatgpt` | ChatGPT 页面 | `open-chatgpt` | 打开官网并识别是否已进入登录态。 |
| `auth` | 认证页 | `existing-account-login`、`fetch-existing-login-code` | 使用已有账户登录并处理登录验证码。 |
| `checkout` | Checkout 页面 | `plus-checkout-create`、`hosted-checkout-submit` | 创建 Plus Checkout，并在 Hosted Checkout 页面填写信息。 |
| `paypal` | PayPal 页面 | `hosted-paypal-payment` | 处理 PayPal Hosted 登录、验证码、账单确认和授权。 |
| `success` | 开通结果 | `plus-activation-success` | 确认 Plus 开通成功并记录结果。 |

页面状态由节点状态派生，不新增独立持久状态。派生规则：

- 页面内存在 `running` 节点：页面状态为 `running`。
- 页面内存在 `failed` 或需要用户确认的恢复建议：页面状态为 `needs_action`。
- 页面内所有节点均为 `completed`、`manual_completed` 或 `skipped`：页面状态为 `completed`。
- 页面内已有部分完成但仍有未完成节点：页面状态为 `partial`。
- 页面内所有节点均为 `pending`：页面状态为 `pending`。

## 侧边栏结构

侧边栏主列表展示页面，而不是直接展示节点 ID：

1. ChatGPT 页面
2. 认证页
3. Checkout 页面
4. PayPal 页面
5. 开通结果

每个页面行显示页面状态、当前进度和主要动作。页面可展开查看底层节点状态，方便调试，但默认不要求用户理解节点 ID。

当后台返回恢复建议时，侧边栏顶部显示恢复建议卡片：

- 标题：简短说明建议动作。
- 描述：说明为什么可以恢复，以及恢复后会从哪里继续。
- 主按钮：执行推荐恢复动作。
- 次按钮：从该页面重新执行，作为建议不适用时的保守入口。

## 恢复建议

后台新增派生能力，基于 `nodeStatuses`、`currentNodeId`、`plusCheckoutTabId`、当前可识别标签页 URL 和失败节点生成 `recoverySuggestion`。

建议优先级从高到低：

1. 当前标签页已是 ChatGPT 登录态，并且认证页未完成：建议标记认证页相关节点为跳过或完成，从 Checkout 页面继续。
2. 当前认证页停留在验证码页，并且 `fetch-existing-login-code` 未完成：建议继续认证页验证码节点。
3. 当前标签页是 Hosted Checkout URL，并且 `hosted-checkout-submit` 未完成：建议接管当前 Checkout 页面继续填写。
4. 当前标签页是 PayPal Hosted URL，并且 `hosted-paypal-payment` 未完成：建议接管当前 PayPal 页面继续支付。
5. 没有可识别页面但存在失败节点：建议从失败节点所在页面重新执行。

建议只生成一个主建议，避免用户面对多个恢复入口时无法判断。

## 恢复动作

恢复动作由后台执行，侧边栏只发送确认请求。

### 已有账户已登录

触发条件：

- 当前 ChatGPT 标签页可识别为已登录态。
- `existing-account-login` 或 `fetch-existing-login-code` 未完成。

动作：

- 将 `open-chatgpt` 标记为 `completed`。
- 将 `existing-account-login`、`fetch-existing-login-code` 标记为 `skipped` 或 `completed`。如果没有实际执行验证码提交，优先使用 `skipped`，因为这能表达“由于已有登录态而跳过”。
- 从 `plus-checkout-create` 继续执行。

### 认证页验证码恢复

触发条件：

- 当前认证页可识别为验证码输入状态。
- `existing-account-login` 已完成或可跳过。
- `fetch-existing-login-code` 未完成。

动作：

- 保留已有登录身份信息。
- 从 `fetch-existing-login-code` 继续执行。
- 不重新提交邮箱和密码，降低重复登录触发风控的风险。

### Hosted Checkout 接管

触发条件：

- 当前标签页 URL 匹配 `https://pay.openai.com/c/pay/*` 或 `https://checkout.stripe.com/c/pay/*`。
- `hosted-checkout-submit` 未完成。

动作：

- 将当前标签页登记为 `plusCheckoutTabId`，并更新对应 source 的标签页记录。
- 确保 `plus-checkout-create` 已完成或跳过。若当前页面就是可用 Checkout，优先标记为 `completed`，因为后续无需重新创建订单。
- 从 `hosted-checkout-submit` 继续执行。

### PayPal Hosted 接管

触发条件：

- 当前标签页 URL 可识别为 PayPal Hosted 支付页面。
- `hosted-paypal-payment` 未完成。

动作：

- 保存当前 PayPal 标签页到运行态。
- 确保 Checkout 页面已完成。
- 从 `hosted-paypal-payment` 继续执行。

### 失败页面重试

触发条件：

- 没有可识别当前页面。
- 存在 `failed` 节点。

动作：

- 找到失败节点所属页面。
- 从该页面第一个未完成节点重新执行。
- 不自动跳过前置页面，除非前置页面已是完成状态。

## 后台接口

新增侧边栏查询消息：

```js
{
  type: 'GET_PAGE_RECOVERY_STATE',
  source: 'sidepanel'
}
```

返回结构：

```js
{
  pages: [
    {
      pageId: 'checkout',
      title: 'Checkout 页面',
      status: 'needs_action',
      nodeIds: ['plus-checkout-create', 'hosted-checkout-submit'],
      activeNodeId: 'hosted-checkout-submit'
    }
  ],
  recoverySuggestion: {
    kind: 'adopt-current-checkout',
    title: '接管当前 Checkout 页面',
    message: '检测到当前标签页是 Hosted Checkout，可继续填写而不重新创建订单。',
    pageId: 'checkout',
    primaryLabel: '接管当前 Checkout',
    secondaryLabel: '从 Checkout 页面重新执行'
  }
}
```

新增侧边栏恢复消息：

```js
{
  type: 'RESUME_FROM_PAGE',
  source: 'sidepanel',
  payload: {
    pageId: 'checkout',
    suggestionKind: 'adopt-current-checkout'
  }
}
```

后台收到恢复消息后重新校验当前状态，避免侧边栏展示建议后页面已经变化。校验失败时返回清晰错误，例如“当前标签页不再是 Hosted Checkout 页面，请重新检测恢复建议”。

## 数据流

1. 侧边栏初始化时读取 `GET_STATE`，随后读取 `GET_PAGE_RECOVERY_STATE`。
2. 后台根据当前状态和标签页生成页面列表与恢复建议。
3. 侧边栏渲染页面步骤和恢复建议。
4. 用户点击主恢复按钮。
5. 侧边栏发送 `RESUME_FROM_PAGE`。
6. 后台重新校验当前页面和节点状态，修正必要节点状态与 tabId。
7. 后台调用现有自动运行继续能力，从目标节点继续执行。
8. 侧边栏通过已有 `NODE_STATUS_CHANGED`、`DATA_UPDATED`、`AUTO_RUN_STATUS` 消息刷新展示。

## 错误处理

- 当前页面无法识别时，不生成强恢复建议，只提示从失败页面重新执行。
- 恢复建议执行前必须重新校验当前标签页 URL 和节点状态，防止用户切换页面后误接管。
- Hosted Checkout 接管只在 URL 匹配已知 Checkout 域名时允许执行，避免把无关页面登记为 `plusCheckoutTabId`。
- PayPal Hosted 接管只在页面可识别为 PayPal 支付链路时允许执行，避免误处理普通 PayPal 页面。
- 已有登录态跳过认证时使用 `skipped` 表达原因，日志必须说明“检测到已有登录态，因此跳过认证页并继续 Checkout”。

## 测试计划

新增或更新以下测试：

1. 步骤定义测试：PayPal Hosted 默认流程中的每个节点都有页面分组。
2. 页面派生测试：节点状态能派生出 5 个页面状态，且完成、部分完成、失败状态计算正确。
3. 恢复建议测试：当前已是 ChatGPT 登录态时，推荐从 Checkout 页面继续。
4. 恢复建议测试：当前 Hosted Checkout 标签页存在且 `hosted-checkout-submit` 未完成时，推荐接管 Checkout。
5. 恢复动作测试：接管 Checkout 后保存 `plusCheckoutTabId`，并从 `hosted-checkout-submit` 继续。
6. 恢复动作测试：PayPal Hosted 页面接管后从 `hosted-paypal-payment` 继续。
7. 侧边栏静态测试：主步骤渲染页面标题，不把节点 ID 当作主步骤展示。
8. 自动运行回归测试：普通自动运行仍以 `mode: restart` 从首节点开始。

## 实施边界

本设计适合一次实现计划完成，改动范围集中在：

- 步骤定义元数据。
- 后台页面状态和恢复建议派生模块。
- 后台恢复消息处理。
- 侧边栏页面步骤渲染。
- 相关单元测试和中文文档。

不需要调整支付内容脚本的页面填写逻辑；Hosted Checkout 接管应复用现有 `executeHostedCheckoutSubmit` 能力。
